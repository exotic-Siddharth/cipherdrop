## Integration needs

- No schema or migration change is required. The admin review grant is audited as `DROP_OPENED` with metadata `{adminReview: true}` because `AuditAction` has no review action; if a dedicated action (for example `ADMIN_REVIEW_GRANT`) is wanted, add it to the enum in schema.prisma plus a migration, then switch the single call in `apps/api/src/modules/admin/service.ts` (reviewGrant).
- W2a uploader (apps/web/src/crypto/uploader.ts, sendFlow.ts) must send `X-Chunk-SHA256` as lowercase hex of the exact ciphertext chunk, `Content-Type: application/octet-stream` and a correct Content-Length; the server checks token, status, file, index, hash format and declared length before reading the body. A rejected body up to MAX_CHUNK_BYTES + 64 KiB is drained so the browser sees the 4xx; larger or length-less bodies get `Connection: close`.
- W2a downloader: chunk GET errors are 401 (unknown or expired grant, or a grant of another drop) and 410 with the reason (blobs gone, DELETED, DISABLED, EXPIRED); a mid-stream storage failure aborts the connection rather than ending a short body cleanly, so the client sees a network error (retryable per R14), never a silently truncated chunk.
- W2a resume (R11): `GET /api/drops/:id/upload-status` returns `{files: [{id, chunkCount, received: [{index, sha256}]}]}` with `sha256` in lowercase hex, sorted by index; it answers 409 once the drop is no longer UPLOADING.
- I1 seed / e2e: the cleanup scheduler is already started by index.ts (`startCleanupScheduler(ctx)`, `stop()` on shutdown) under the Redis lock `${KEY_PREFIX}:lock:cleanup`, with a first pass at boot; e2e runs that depend on fixed drop states should use their own KEY_PREFIX and a large CLEANUP_INTERVAL_SEC.
- B1 `/me/drops` (R6): cleanup purges the blobs of EXHAUSTED drops only once no grant is live, and the status stays EXHAUSTED; owner-deleted drops become DELETED; `blobsDeletedAt` marks purged drops. Nothing else is needed from B1.

## Decisions

- 2026-11-08: Quota at create counts `storageUsedBytes` plus the ciphertext bytes of the owner's own UPLOADING drops, so parallel uploads cannot overshoot the quota; `storageUsedBytes` itself is incremented only on complete (READY) and released exactly once when the blobs are purged (owner delete, admin disable, expiry, exhaustion cleanup).
- 2026-11-08: `purgeDropBlobs()` (modules/drops/lifecycle.ts) is the single blob-deletion path: storage first (idempotent), then a conditional `blobsDeletedAt` update that releases the quota, so racing cleanup, owner delete and admin disable never double-release. Cleanup also sweeps terminal drops whose earlier purge failed, and deletes grants expired for more than 24 h.
- 2026-11-08: Admin review grants are audited on the admin's own log as `DROP_OPENED` with `{adminReview: true}` (no dedicated enum value exists); they never consume a download.
- 2026-11-08: Reports are audited to the drop owner as `DROP_REPORTED` without the reporter's ipPrefix (the owner must not learn it); the reporter's ipPrefix is stored on the Report row, visible to admins only.
- 2026-11-08: Meta, unlock, open and report answer 404 for a drop still UPLOADING (recipients cannot tell it from an unknown id); gone drops answer 410 with the reason.
- 2026-11-08: Chunk PUT checks everything that does not need the body (upload token, status, file, index, X-Chunk-SHA256 format, declared Content-Length) before reading it, then express.raw buffers at most the chunk ciphertext size; rejected bodies of verified uploaders are drained so browsers receive the error status instead of a connection reset.
